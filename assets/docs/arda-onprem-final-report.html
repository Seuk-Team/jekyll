2.발생한 오류와 수정 내역 (증상 → 원인 → 수정)

2-1. Watchdog .ps1 파서 오류

증상register-watchdog.ps1/wsl-watchdog.ps1 가 PowerShell 5.1 에서 파싱 실패 원인한글 주석 + 따옴표 손실(Start-Process -ArgumentList "-c","sleep infinity" 의 따옴표 벗겨짐)
수정 — ASCII 전용 재작성 + 인자를 '"sleep infinity"' 로 따옴표 보존. keepalive 정상(result=0). 교훈: .ps1 은 영문 전용 + 전달 전 ParseFile/dry-run.

2-2. STT 답변이 "자기 멋대로" 저장됨 가장 오래 헤맴

증상면접 답변 전사가 첫 답변 빼고 엉뚱하게 저장. AWS 에선 멀쩡 오진STT 엔진(CPU whisper) 문제로 의심 → GPU 시도(이미지에 CUDA 없어 실패), OpenAI 키 필요한지 검토 진짜 원인엔진이 아니라 컨테이너 재기동 타이밍. STT 설정을 바꾸며 PC2 lie-detection 을 면접 진행 중에 4번 재기동. 답변 음성은 파일이 아니라 컨테이너 메모리에만 있어(PROTOCOL.md) 재기동 시 그때까지 발화가 사라지고, 재접속 뒤 조각만 전사 → "첫 답변만 멀쩡"
검증 — 한국어 TTS 답변 4종을 실제 프로토콜로 흘려 넣는 재현 클라이언트 작성. PC2 직결·터널경유 12/12 정확 전사(답변당 7.5초). 즉 온프레 STT 엔진 자체는 정상(엔진 문제 아님).
수정 — 면접 중 lie-detection 재기동 금지 규칙화 · 내가 넣은 STT_TIMEOUT_SEC=60 제거(기본 180 복원)

2-3. 서류 요약 점수가 전원 64~65점으로 수렴 변별력 상실

증상온프레미스 요약 재생성 시 모든 지원자 64~65점. AWS(Haiku)에선 정상 원인chain_evaluate.v2 프롬프트의 출력 예시 숫자 70/40/60 을 소형 모델(qwen3)이 그대로 베낌. Claude 는 안 베껴서 AWS 에선 안 드러남
수정 — chain_evaluate.v3: 예시 숫자 제거, 채점 구간표+절차 명시, 요건 비면 공고 제목 사용. 실측: 문해린 85·한지우 85·오하람 40·한도윤(디자이너) 15 ↔ Haiku 78·86·44 와 같은 방향 (커밋 6daaf32). ※ v9 채팅 어댑터는 요약에 부적합(<tool_call> 냄) → 전용 arda-summary 유지

2-4. 요약 JSON 파싱 실패로 점수 NULL

증상56명 재생성 중 2명 서류점수 NULL(step2 파싱 실패) 원인소형 모델이 문자열 안에 이스케이프 안 된 따옴표를 써서 JSON 깨짐. Ollama format 스키마도 못 막음
수정 — 파서에 문자열 내부 따옴표 복구 폴백(_repair_inner_quotes) 추가. 정상 JSON 은 그대로 (커밋 615357d). 이후 56/56 파싱 성공

2-5. 이력서 미리보기: 브라우저가 MinIO 에 못 닿음

증상이력서 클릭 시 안 열림 원인presign 다운로드 URL 이 minio:9000(컨테이너 내부 호스트) → 브라우저에서 이름이 안 풀림
수정 — 파일 본문을 Postgres file_blobs 에 넣고 1회용 티켓 API URL 로 스트리밍(inline 미리보기). PUBLIC_API_BASE_URL 로 절대 URL 스킴 고정(mixed-content 해결)

2-6. 이력서 업로드: 브라우저가 MinIO 에 못 올림 폐쇄 직전 발견

증상아르 채팅 이력서 드롭 / 공개 지원폼에서 "올리지 못했습니다" 원인업로드도 presign 으로 브라우저가 minio:9000 에 직접 PUT → 온프레에선 못 닿음. 공개 지원폼도 같은 코드라 온프레에선 아무도 브라우저로 이력서 못 올림
수정 — 업로드도 api 경유(커밋 0413840). presign-upload 가 온프레면 api PUT URL(/files/blob-put, 1회용 티켓)을 주고 서버가 MinIO 에 저장. 다운로드도 blob 없으면 MinIO 서버측 스트리밍. AWS(실 S3)는 기존 그대로. 터널 실측: PUT 200, MinIO 저장·티켓 1회용 확인

2-7. STT/ViT GPU 이전 부하 대비 · 옵션 완료

동기"여러 명 동시 접속 시 터지나" — 8명 동시 부하테스트: 서버는 안 죽지만 STT 대기줄 15→42초 증가(CPU, Semaphore(1) 직렬화). 터짐이 아니라 느려짐 결과lie-detection GPU 변형 이미지(python:3.13-slim + torch cu124 + LD_LIBRARY_PATH) 빌드 + compose GPU 할당. 실측: 전사 7.5초→~1초, 8명 동시에도 대기줄 0, 정확도 동일. (커밋 안 함 — PC2 로컬 파일, 롤백 즉시)

2-8. 아르 채팅 이력서 접수(create_application) 폐쇄의 결정타

증상업로드는 성공했으나 접수에서 반복 실패 — "공고를 찾을 수 없습니다"(없는 posting_id) · "서버에 연결하지 못했습니다" 원인로컬 sLLM(qwen3 v9)이 다단계 도구 흐름을 못 지킴. list_postings 로 실제 공고 id 를 확인하지 않고 create_application 을 한 번에 호출하며 posting_id 추측(rounds=1). 안내를 줘도 추측 반복 판단프롬프트/데이터로 매번 땜질해야 하는 로컬 모델 한계. AWS 는 Claude 라 도구 체인을 안정 수행 → 이 부류 오류 없음 → 온프레 폐쇄 결정

3.폐쇄 사유 (정리)

  1. 로컬 sLLM 도구호출 불안정 — create_application 이 list_postings 건너뛰고 posting_id 추측. 채팅 접수·복잡 도구 흐름을 심사에서 신뢰 불가 (2-8)
  2. 브라우저↔내부 MinIO 불가 — 업로드/다운로드를 api 프록시로 우회(고쳤지만 온프레 고유 복잡도). AWS 는 실 S3 라 애초에 문제 없음 (2-5, 2-6)
  3. 온프레 고유 실패가 프리즈(09-20) 직전 누적 — 예시숫자 베끼기·JSON 따옴표·재기동 타이밍 등 전부 "AWS 에선 안 나던" 것들. 심사 안정성 최우선
  4. 결론 — 심사는 검증된 AWS 스택(Claude + 실 S3 + 관리형 인프라)에서 진행. 온프레는 발표 자료·학습 성과로 보존
