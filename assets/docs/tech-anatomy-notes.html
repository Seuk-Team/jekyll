신규_seed_questions_bg — 자소서·이력서·공고에서 꼬리질문 10개

세션 생성 API 응답을 지연시키지 않고 뒤에서 도는 BackgroundTask. LLM 3~5초, 그 사이 담당자는 이미 링크 복사 화면.

왜 필요
ADR-0026 §5-5 지시서에 자동 질문 생성이 설계돼 있었지만, 그동안은 담당자가 손으로 텍스트에어리어에 넣어야 지원자가 시작할 수 있었다. Daniel Kim · 류성민 처럼 자소서가 이미 있는 지원자에게 담당자가 매번 같은 작업을 반복.

def expressions_from_frame(frame, top_k: int = 3) -> list[dict] | None:
    if not VIT_MODEL: return None
    lm, rgb = _detect(frame)             # mediapipe · 얼굴 랜드마크
    if lm is None: return None
    crop = _crop_of(lm, rgb)             # 랜드마크 덮는 사각형만
    if crop is None: return None         # < 60px 면 폐기
    probs = expression_rows([crop])      # ViT 로 7종 확률
    if not len(probs): return None
    labels = _vit_labels()               # id2label
    row = probs[0]
    order = np.argsort(row)[::-1][:top_k]
    return [{"label": labels[int(i)],
             "label_ko": _EXPRESSION_KO.get(labels[int(i)].lower(), labels[int(i)]),
             "prob": round(float(row[i]), 3)} for i in order]

4. STT 상한 45s → 180s · 3분 답변 커버faster-whisper CPU 실측 1.8배속 기준 재계산

개정STT_TIMEOUT_SEC · 계산 근거 재수립

기존 45초 상한이 "int8 4배속 가정" 이었지만 실측은 1.8배속. Daniel Kim 98초·63.8초 답변이 자리표시자로 저장되던 것을 실측 뒤 180초로 상향.

왜 바꿨나
실측 DB (2026-09-10 저녁): 
| seq | question | 저장된 답변                |
|-----|----------|-----------------------------|
|   1 | 3k 동시…  | [전사 지연 · 발화 98.0초]  |  ← 상한 초과
|   2 | disconnect… | [전사 지연 · 발화 63.8초] |  ← 상한 초과
CPU int8 실측 1.8배속 (ADR-0032 §근거) 이므로 3분 발화 = 100초 처리. 상한 45초는 첫 3분 답변에도 못 미친다. 면접은 3분 이상 이야기하는 자리(팀장 지적).

# 로 3분 발화가 100초 안에 처리되고, 여기에 여유 80초를 더한 180초로 상향한다.

#

무해한 이유
전사는 별도 스레드. 면접 흐름은 다음 질문 이미 받아 뒀으므로 지원자를 대기시키지 않는다 (submit_answer 흐름 · fetch_questions 로 다음 질문 미리 받음). STT 스레드가 CPU 를 오래 잡는 동안에도 이벤트 루프는 계속 돌아 다음 답변을 받는다.
남는 한계
5분 이상 답변은 CPU 로 여전히 불가. 300초 발화 → 165초 처리, 상한을 어떻게 늘려도 CPU 가 답변 페이스 못 따라감. 동시 지원자 여러 명도 CPU 병목. GPU 만이 진짜 해결 (T4 30배속, 3분 답변 → 6초, 10분 답변 → 20초).
2026-09-18 갱신 · STT 는 OpenAI whisper-1 API 로 서빙한다
OpenAI whisper-1 실시간 전사가 프로덕션 기본이다 (ADR-0038 · 분당 $0.006 → 면접당 ~$0.06). 무음 구간 hallucination(빈 소리에 없는 말을 지어냄)은 no_speech_prob 게이트로 완화했다. 로컬 faster-whisper large-v3-turbo 경로는 폴백으로 코드에 남아 있고, 아래 §4 의 CPU int8 180초 상한 논리는 그 로컬 경로 실측 당시의 기록이다.
GPU 실측(Tesla T4): faster-whisper large-v3-turbo CUDA fp16 275ms/3s — 로컬 경로를 GPU 에서 돌렸을 때의 참고 수치다.

8. ADR-0028 §1.7단계 · 우회의 흔적을 남긴다PR #173 · 소유자가 뚫어도 자국이 남게

문서ADR-0028 §1.7단계 세 갈래

1.6단계 (권한 분리) + 관리 비밀번호 분리로도 테이블 소유자는 여전히 ALTER TABLE ... DISABLE TRIGGER 로 append-only 잠금을 뚫을 수 있다. 막을 수는 없지만 — 우리 서버니까 — 뚫으면 반드시 자국이 남게 할 수 있다.

왜 필요
1.6단계까지의 한계: 관리 비밀번호를 아는 사람은 여전히 원장을 다시 쓸 수 있다. ADR-0028 서두의 원칙 ("우리는 못 막을 수 있지만, 고친 사실이 밖에서 드러난다") 을 DB 층에서도 반복 적용.
세 갈래 (구현 미완 · 팀 결정)
  • ① Event trigger 로 트리거 상태 변경을 append-only 감사 로그에 기록 — PostgreSQL 의 DDL 이벤트 트리거(ddl_command_start · ddl_command_end) 를 잡아 ALTER TRIGGER 이벤트를 document_anchors_trigger_audit 에 append. 이 감사 표에도 append-only 트리거를 걸면 우회는 감사 로그 자체까지 지워야 가능해진다.
  • ② document_anchors.tgenabled 를 주기 감시 · 변경 시 알림 — pg_trigger.tgenabled 를 1분마다 확인하는 헬스체크. 'D' (disabled) 로 바뀐 순간 슬랙 · 이메일 · 팀 채널에 알림. 이미 있는 n8n 워크플로 구조로 가볍게.
  • ③ Sepolia 게시 시점에 원장 검증 · 어긋나면 게시 중단 — chain_publications 배치가 돌 때 seq 구멍 · chain_hash 사슬 무결성 확인. 어긋난 것이 있으면 게시 중단 + 알림. 뚫린 상태를 밖으로 못 나가게 한다.
우선순위
③ > ② > ①. ③이 외부 증명 신뢰도를 지키는 값이 크다. ② 는 가장 값싸다 (n8n 헬스 하나). ① 은 DDL 이벤트 트리거 도입이라 검토 필요.
목적
봉인이 아니라 문턱·자국. 셋 다 붙으면 누구도 조용히 못 뚫는다 — 뚫으면 반드시 감사 로그 · 알림 · 게시 중단 셋 중 하나에 자국.

9. 잠긴 원장 뚫기 · 실전 절차 · 뒤처리fit-check 24명 재접수 · 트랜잭션 하나로 처리

안전 장치
  • 트랜잭션 원자성 — BEGIN...COMMIT 사이 어디서든 실패 시 자동 ROLLBACK → 트리거 상태·데이터 다 되돌림.
  • DDL 문도 트랜잭션 안 — PostgreSQL 의 ALTER TABLE 은 트랜잭션 내에서 롤백 가능.
  • 커밋 뒤 검증 필수 — SELECT tgname, tgenabled FROM pg_trigger WHERE tgname='trg_document_anchors_append_only' 로 'O' (ENABLED) 확인.
  • 스크립트 사후 삭제 — rm wipe_fit_check.sql · 서버·컨테이너·로컬 모두. 뚫은 방법이 남아 있으면 다시 뚫릴 수 있다.
